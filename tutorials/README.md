## Conformance notes

_Requirement identifiers in these notes (for example `ST1`, `PAR3`, `DAT24`, `EVAL21`) are the NOTEBOOK_SPEC 1.1 numbering they were written against; NOTEBOOK_SPEC 2.0 renumbered its sections and the pull request that migrated this repository reports conformance against the 2.0 pre-flight checklist (§26) and report format (§30)._

- **Standalone carrier (ST1–ST6):** the primary path performs no clone, repository install or repository import (the previous pair's `git clone` of this repository and its `%pip install -r` are gone: the module is carried instead). Section 2 of each notebook is `mitra_pipeline/tutorial_api.py` verbatim (one cell tagged `metadata.dimer.embedded_module`; the only rewrite makes `DEFAULT_WEIGHTS_DIR` working-directory-relative), Section 3 carries the model identity and the two-file SHA-256 manifest inline and asserts they agree with the module before anything is fetched, and Section 1 carries the exact `pyproject.toml` runtime pins. `metadata.dimer.generated_from` records the repository, the generating commit, the module SHA-256 and the generator version.
- **Parity (PAR1–PAR4):** `tests/test_notebook_parity.py`, `tests/test_companion_parity.py` and `tools/validate_release_assets.py` fail when the carried module, the inline manifest, or the inline pins differ from the repository, or when a notebook is not byte-identical to the generator's output for its template.
- **Model acquisition:** `stage_missing_files(WEIGHTS_DIR, allow_download=True)` fetches only the manifest entries that are absent, from the Hugging Face Hub at the immutable revision (never `main`); `verify_snapshot` re-hashes them and asserts the manifest digests equal the package's `WEIGHTS_SHA256` / `CONFIG_SHA256`; `MitraClassificationPipeline.from_pretrained(weights_dir=WEIGHTS_DIR)` then calls the existing `stage_verified_hf_snapshot`, which stages the verified bytes as the immutable offline Hugging Face snapshot AutoGluon resolves (`HF_HUB_OFFLINE`). The previous `MODEL_SOURCE = "DIMER ZIP"` option is replaced by the snapshot directory: place the two files there and nothing is downloaded (`validate_dimer_model_package` remains in the API for DIMER packages).
- **Role stages:** `validate_inputs` (DAT24) writes `outputs/<stem>_input_manifest.json` with the schema, the observed structure of every table (the `validate_labeled_frame` report with dropped missing-target rows and exact duplicates — never hidden, DAT23), the verdict and one recorded rejection finding; `evaluation_report` (EVAL21) writes `outputs/<stem>_evaluation_report.json` — `sample-sanity` with `accuracy` / `balanced_accuracy` / `log_loss` / `roc_auc` / `f1_macro` / `mcc`, the independent-test block and the majority-class baseline in the E2E notebook (the executable-baseline table is attached), `not-measurable` (with what labelled data would make the task measurable) in the companion.
- **Artifact-inference companion (§18):** the bundle is supplied from outside the execution (upload, or `ARTIFACT_ZIP_PATH` for executors); a trusted whole-archive SHA-256 is required by default (`ALLOW_UNVERIFIED_ARTIFACT` is an explicit override); `safe_extract_archive` rejects absolute paths, traversal, backslash paths, symlinks, suspicious compression ratios, oversized members and oversized expansion; `validate_artifact_directory` verifies the inventory, sizes, digests and provenance, the base-model identity/digests are compared with the carried pinned values and the AutoGluon/Python versions are checked, all before `TabularPredictor.load(...)`; no bundle is created and nothing is fitted in the companion.
- Classification obligations (Notebook Specification §20.1): the class list, class counts and the majority-class share are printed before the model runs and every holdout/test class must be present in the support rows (`require_class_coverage`); the decision rule is `argmax` over uncalibrated class probabilities (no threshold is shipped); accuracy, balanced accuracy, macro F1 and MCC are the discrete correctness measures, log loss and ROC-AUC the probability/ranking measures; exported `probability_<class>` columns keep the predictor's class order, and classical-baseline probabilities are aligned to that order with `align_probabilities` before scoring.
- `USE_BYOD`, `RUN_FINE_TUNING` and `RUN_NEW_DATA_INFERENCE` (E2E) and `ALLOW_UNVERIFIED_ARTIFACT` (companion) default to `False`.
- `tools/validate_release_assets.py` performs source validation only. It does not satisfy the clean-runtime execution requirement; a release review must confirm that a recorded clean run in `../docs/release-verification.md` matches the notebook revision under review before the status is promoted to `Release-grade`.

## Data and evaluation

The tutorial sample portfolio is pinned to repository revision `f11bf59d1bb7e75de42145e311de9773fda1607a`, matching the `SAMPLE_REVISION` embedded in the E2E notebook. It contains:

- `freshretailnet-h7.zip` — leakage-aware temporal demand classification derived from FreshRetailNet-50K;
- `insurance-medical-charges.zip` — cross-sectional medical-cost classification; and
- `ames-housing.zip` — cross-sectional residential-price classification.

All are tutorial/sanity fixtures, not benchmark evidence. Their source/provenance and licence notes are documented in [`../examples/sample-data/DATASET_CARD.md`](../examples/sample-data/DATASET_CARD.md).

For the default FreshRetailNet path, the literal CPU tutorial deterministically uses 512 training rows and 256 rows from each evaluation partition as a bounded smoke subset; users can raise the notebook controls to use more or all rows. BYOD paths are unaffected. A BYOD single-CSV path uses a deterministic random holdout and explicitly assumes approximately IID rows. Time-dependent, grouped, panel, embargoed, patient/device-level, spatial, or otherwise leakage-sensitive workflows should provide pre-split train/validation/test files.

Classification evaluation includes an executable majority-class baseline rather than quoted development-run numbers. Accuracy, balanced accuracy, log loss and ROC-AUC remain in target units; R² is complementary. Sample values must not be generalized to other datasets.

## Artifact contract

The E2E tutorial exports `mitra-predictor.zip`. The archive contains the selected AutoGluon predictor plus:

- `tutorial_run_metadata.json` — model/revision, runtime, data identity, selected variant, adaptation configuration, metrics, feature order, target, and provenance;
- `artifact_manifest.json` — format/version and complete file inventory with size and SHA-256 for every other artifact file.

Because Mitra inference uses support/training context and AutoGluon preprocessing state, the exported predictor may contain or encode information derived from source data. Apply the source dataset's confidentiality, licensing, disclosure, and retention rules to the artifact.

Path safety and manifest consistency do not make Python serialization safe. Only load predictor ZIPs from trusted producers. The artifact-inference notebook requires a trusted whole-archive SHA-256 by default; bypassing that check is an explicit expert override.

The optional DIMER offline model ZIP has its own normative manifest contract documented in [`DIMER_MODEL_PACKAGE.md`](DIMER_MODEL_PACKAGE.md).

## Release verification

The release gate, the executor procedure for both notebooks and the durable execution record live in [`../docs/release-verification.md`](../docs/release-verification.md). Static checks run in ordinary CI:

- the standalone carrier and parity checks (`tools/validate_release_assets.py`, `tools/build_notebook.py --check`, `tests/test_notebook_parity.py`, `tests/test_companion_parity.py`);
- the repository-specific spec-1.1 checks (`scripts/validate_colab_tutorial.py`), conformance markers and absence of placeholder text;
- CSV/header classification checks against the package and the generated notebooks;
- public API archive/manifest and DIMER-package classification tests.

A separate **Notebook release execution** workflow executes the current E2E default path in a clean hosted runner, produces a predictor artifact, derives new inference rows, and executes the `ARTIFACT-INFERENCE` notebook against that externally produced artifact with its trusted SHA-256. The workflow records actual step outcomes and fails closed unless the producer, digest preparation, and consumer execution all succeed. A release claim must cite the successful workflow/PR head; static CI alone is not execution evidence.
